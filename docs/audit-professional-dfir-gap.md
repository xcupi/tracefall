# Audit: gap analysis to a professional DFIR tool

Scope: what Tracefall lacks to become a tool where an examiner uploads a
disk or memory image, gets automatic analysis and a best-practice
forensic report with no LLM, plus an optional LLM layer for
interpretation and narrative.

Method: source reading, grep over `internal/` and `cmd/`, repository docs,
and one full `go test -timeout 30m ./...` run (passed; `internal/api`
alone took about 11 minutes). No real forensic image was run through the
product. Everything below is source inspection, not runtime verification
against real evidence. All tests use synthetic fixtures generated by the
repository's own `*gen` packages.

## Verdict

Tracefall today is a triage and investigation platform for already
extracted Windows artifacts (KAPE ZIP, AD1 logical image). About 55k
lines of non-test Go, two dependencies, fully deterministic. That is a
sound foundation. The headline goal (upload a disk or memory image, get
automatic analysis and a professional report) is roughly 25-30% met. The
missing parts are the heaviest: image readers, memory analysis, and
reporting.

## P0: blockers for the stated goal

### 1. Disk image reader (partly done)
- Done: E01 (EWF1) and raw disk images, MBR/GPT partition tables, NTFS
  reading (`internal/image`, `internal/ntfsvol`). Validated end to end on a
  real E01 (156/156 file hashes match, see `docs/disk-images.md`).
- Not done: EWF2 (Ex01) is refused explicitly; VMDK, VHD/VHDX, qcow2 and
  AFF4 are absent; ext4, FAT/exFAT, APFS and HFS+ filesystems are only
  recognised from the partition table, not read; BitLocker is detected
  with no way to supply a key.
- `internal/ntfs` parses extracted `$MFT`, `$UsnJrnl`, `$LogFile` files;
  it is not a volume or filesystem reader.
- No BitLocker/encryption detection, no deleted-file carving, no ext4,
  FAT/exFAT or APFS.
- Acceptance: upload an E01 and a raw image of a Windows system disk;
  partitions are enumerated, NTFS volumes are opened read-only, relevant
  artifacts are located and extracted automatically into the existing
  parser path; embedded acquisition hashes are verified at ingest and a
  mismatch is surfaced; unsupported/encrypted images fail with a clear
  reason, never as an empty success.

### 2. No memory analysis

**Status: Partly done (roadmap item 4).** Volatility 3 is wrapped in a bubblewrap
sandbox and its output normalised to events; see `docs/memory-analysis.md`.
Validated on real authorised Reveal, Ramnit and RedLine dumps. The baseline
found identity collisions after parsing; the scoped P0 fix now preserves all
regions, nonempty service names and distinct socket endpoint/state tuples in
fresh cases (42/42 selected checks pass). See `docs/validation-memory-p0.md` for
results and old-case recovery. Broader acceptance remains blocked on detection
and coverage gaps. `docs/validation-cyberdefenders-baseline.md` retains the original
measurements. The historical audit bullets below describe the pre-implementation
state, not current memory capability.

- `ARCHITECTURE.md:15` lists memory forensics as out of scope.
- `hiberfil.sys`, `memory.dmp`, `memory.raw` are only cataloged and
  hashed (`docs/evidence-triage.md:135-151`).
- Minimum needed: format detection (raw, LiME, crash dump, VMEM),
  process list, modules, network connections, command lines, injection
  detection, string/IOC extraction.
- Options: bounded native parser (Windows x64, EPROCESS scan) or an
  isolated Volatility 3 worker whose output is normalized to
  `model.Event`. Recommendation: worker first.
- Acceptance: a public Windows memory sample with known ground truth
  yields the expected process tree and network connections as events
  with provenance to the image and offsets; a corrupt or unsupported
  image is reported, not silently empty.

### 3. Forensic report (done for HTML bundle; PDF and spec items open)
- Done: the pipeline's `report` stage writes a ZIP bundle (report.html,
  manifest.json, findings.csv, timeline.csv) after analysis
  (`internal/api/report_stored.go`). Its SHA-256 and report.html's are
  recorded in the audit log. `GET /api/cases/{id}/report/latest` serves it.
- Open: PDF output; the report does not yet carry every item of the
  specification below (e.g. ATT&CK mapping, appendices).
- Acceptance: see "Report specification" below.

### 4. Pipeline is not hands-free
- Auto-import and auto-analyze exist only as browser JavaScript
  (`internal/web/static/app.js`, `runAutoImportAndAnalyze`). Closing the
  tab mid-run breaks the chain.
- Upload is a single multipart request; unsuitable for tens of GB.
- Segmented AD1 cannot be uploaded through the browser
  (`docs/ad1-ingestion.md:198-209`).
- Acceptance: a server-side job (ingest, parse, analyze, report) that
  survives a browser close and a server restart, with resumable/chunked
  upload or ingest from a server-side path, and per-stage status and
  failure reporting.

## P1: analysis depth and trust in results

### 5. Narrow detection
- 15 rules (`internal/detect/rules.go`): execution, persistence, logon.
- Missing: timestomping ($SI vs $FN data is already parsed in
  `internal/ntfs/mft.go`), event-log clearing (1102/104), shadow copy
  deletion, USB/exfiltration, lateral movement, account manipulation,
  other anti-forensics.
- No Sigma, YARA, IOC/threat-intel matching, or known-file hash sets
  (NSRL / known-bad).
- Acceptance: Sigma rule import with a mapped field model; YARA scan of
  extracted files; IOC list matching; each new rule documented in
  `internal/detect/catalog.go` with base/max severity and basis.

### 6. Artifact coverage gaps
- Unsupported per `docs/evidence-triage.md:117-149`: SRUM and other ESE
  databases (WebCache, Windows.edb), SetupAPI (USB history), ETL, WMI
  repository, Defender logs, RDP bitmap cache, thumbcache, legacy EVT.
- Also missing or unverified: Volume Shadow Copies, `$I30`. ShimCache /
  AppCompatCache needs a check against the registry parser.
- No macOS, Linux or mobile support.

### 7. Timestamps and timezones
- Layouts without offset are treated as UTC (`internal/normalize`).
- Done for one case of data: the host time zone is read from the
  collection's own SYSTEM hive (`internal/timezone`, `ActiveTimeBias`).
  ShellBag DOS dates get a derived `*_utc` value beside the untouched
  local reading; the report states the zone and the basis.
- Open: one fixed offset per collection, so daylight-saving changes are
  NOT applied. Verified on a real image: readings in DST months are off by
  one hour against the IANA zone. UserAssist and other local-time values
  are not converted yet. No clock-skew detection.
- Acceptance: host timezone derived from the SYSTEM hive and recorded
  per collection; local-time artifacts converted with that basis and the
  basis stated in the report.

### 8. Scale
- `AnalyzeCase` loads every event into memory (`ListEvents`, then
  `detect.Run` and `correlate.Run`, `internal/api/service.go` around
  2385-2392). Export and provenance paths do the same.
- One `$MFT` can yield hundreds of thousands of events; a full disk far
  more.
- SQLite runs with `SetMaxOpenConns(1)` (`importjob.go:23`), so a big
  import blocks all other queries.
- Acceptance: analysis and export stream or batch with a bounded memory
  ceiling; reads remain responsive during import; a documented
  throughput/memory benchmark on a multi-million-event case.

### 9. Parser isolation
- Only a `recover()` in the import goroutine (`importjob.go:345`) and
  per-parser size limits. No per-parser timeout, memory limit or process
  sandbox found.
- Acceptance: parsers run in a child process with CPU/memory/time
  limits; a hostile or pathological file fails that file only.

### 10. Validation against real evidence
- ~57k lines of tests, all synthetic fixtures.
- Acceptance: documented runs against public datasets with ground truth
  (e.g. NIST CFReDS, Digital Corpora, Volatility Foundation samples);
  expected-vs-actual results recorded; known discrepancies listed.

## P2: integrity, custody, security

### 11. Custody and audit
- `docs/provenance-and-custody.md:226-246` states this is not legal
  chain of custody. Audit log is in the same database, unsigned; no hash
  chain, HMAC or external timestamp found. Deleting a case deletes its
  audit trail.
- Acceptance: append-only hash-chained audit; signed report manifest;
  examiner fields (name, ID, authority, receipt/hand-off records);
  audit survives case deletion in an exportable sealed form.
- Already good: SHA-256 and SHA-512 at ingest, re-verification, evidence
  never modified.

### 12. Acquisition and write protection
- Read-only handling is a code convention (`O_RDONLY`), not an
  enforced mode. Acquisition hashes embedded in containers are not
  checked against computed hashes.

### 13. Security hardening
- Authentication and CSRF exist (PBKDF2-600k, hashed session tokens).
  No TLS termination, two roles only, no MFA.
- CSV export: no formula-injection protection found in
  `internal/api/export.go` (cells beginning with `=`, `+`, `-`, `@`).
  Verify with a test, then fix.

### 14. Frontend maintainability
- `internal/web/static/app.js` is about 9.3k lines, no build step. UI
  "tests" are source-string assertions (`internal/api/ui_phase14_test.go`),
  which do not prove browser behavior.
- Acceptance: browser end-to-end tests (e.g. Playwright) for upload,
  auto-analysis, timeline, report download.

## Report specification (deterministic, no LLM)

Relevant guidance: ISO/IEC 27037, 27041, 27042, 27043; NIST SP 800-86;
SWGDE; ACPO principles. Output HTML first, then PDF, generated purely
from stored data.

1. Cover and metadata: case ID, examiner, authority, dates, tool and
   parser versions, report hash.
2. Executive summary: findings summarized, each traceable to evidence.
3. Evidence inventory: name, size, acquisition hash, computed hash,
   verification result and time.
4. Methodology: tools, parsers, rules and versions; processing order;
   timezone basis.
5. Findings: severity, confidence, rule and reasoning, ATT&CK mapping,
   source file and record references.
6. Timeline: condensed in body, full in appendix.
7. Coverage and limitations: unsupported artifacts, parse failures, what
   was not analyzed.
8. Appendices: hash manifest, audit log, rule list, glossary.
9. Clear separation of observed fact from interpretation.

Acceptance: the same case produces a byte-identical report on re-run
(apart from a stated generation timestamp); every finding in the report
resolves to a source record; report hash is recorded in the audit log.

## Optional LLM layer

Currently no LLM code exists (comments only). Design constraints:

- Provider abstraction (Anthropic, OpenAI, Gemini, local via
  Ollama/llama.cpp). Default off. Core workflow must not depend on it.
- Uses: executive-summary narrative, plain-language finding
  explanations, suggested next triage steps, Q&A over the timeline,
  translation of the report.
- Guardrails:
  - Send only selected events and findings, never raw evidence; minimize
    or redact sensitive data; explicit confirmation before anything
    leaves the host.
  - Every claim must cite event or finding IDs; the server validates
    that cited IDs exist.
  - Output labeled "AI-assisted, unverified" and kept separate from
    deterministic findings in the report.
  - Prompt, model, version and response logged in the audit trail.
  - The LLM never creates or edits findings, severities or hashes.
- Local-model option for evidence that must not leave the network.

## Suggested order

1. Deterministic report generator (HTML, then PDF) with hash manifest.
2. Server-side pipeline: job queue, restart-safe, resumable upload,
   streaming analysis.
3. Disk image reading: E01/EWF and raw first, then partitions and NTFS
   volume reader, then automatic artifact extraction.
4. Memory: isolated Volatility 3 worker, normalized to events.
5. Detection: Sigma, YARA, IOC, hash sets, anti-forensic rules.
6. Validation on public datasets; parser isolation.
7. Signed audit and custody.
8. LLM layer with guardrails.

Items 3 and 4 are the largest work (months, not days) and involve
complex binary formats.

## Limitations of this audit

- Source and documentation review only; not validated against real
  images.
- Grep-based absence claims (e.g. "no timezone extraction", "no formula
  protection") should be confirmed with a targeted test before acting.
- Test suite status is as of this session; the uncommitted changes in
  the working tree at the time were included in that run.
